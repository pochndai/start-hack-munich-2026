Faster Physics: what we did and why

Our entry for the Feyer challenge at START Hack Munich, 21 to 22 November 2026. This is the team's own record: every improvement, every choice, and what we decided against.

1. The task in plain words

Differometor is a program that simulates a gravitational-wave detector: mirrors, lasers and light paths. For a given design it works out how sensitive the detector is at 101 frequencies, and how that sensitivity changes when each of 193 design values changes (the gradient). It is written in JAX, a Python library that turns calculations into compiled programs and can compute gradients automatically.

The challenge: make it faster without changing its results. What is scored is one complete first run on one processor core, including loading the libraries and compiling. The final test uses a slightly different detector than the example, so nothing may be tailored to the example. Only correct entries are ranked: the sensitivity must match the reference to 0.001%.

2. The five ideas behind the speed-up

IdeaWhat it meansChanges
Skip the zerosThe equations to solve form a table that is 99.5% zeros. A sparse solver only touches the cells that are not zero, and we only build those cells.1, 3, 16
Compile lessIn the original, most of a first run was JAX compiling, not calculating. We first made the compiled program smaller, then moved the calculation into NumPy, which needs no compiling. JAX remains the outer shell, so the function still works with JAX's tools.2, 4, 6 to 12, 15, 17
Do the algebra firstSome work cancels out or can be shared: one of three solves per frequency was not needed, and the gradient can reuse what the forward calculation already has.5, 16, 20
Derivatives only where neededThe physics formulas were differentiated with respect to all seven of their inputs. Only inputs that depend on a design value matter.14
Mind the machineLoading libraries, memory handed back and forth with the operating system, and settings of the solver all cost time on one core.18, 19, 21

4. Every change, one by one

Stage A: a smaller compiled program (changes 1 to 11)

No.ChangeWhat and whyEffect
1Sparse solverThe signal equations are solved with KLU, a solver for sparse tables, in place of a dense solver that works through every cell.Forward run 13.8 s to 4.5 s
2Group cells by formulaJAX is told up front which physics formula fills which cell, so each formula is compiled once and only where it is used.Compile 23.5 s to 14.2 s
3Sparse assemblyOnly the non-zero cells of each table are built and stored.Forward run 4.3 s to 0.16 s; memory 8.7 GB to 1.0 GB
4Quick-compile settingsThe compiled program runs for a fraction of a second, so the compiler is asked to produce plain code quickly and skip the slow polishing.Compile 14.0 s to 3.7 s
5Drop the third solveAlgebra shows that one of the three solves per frequency cancels out. The derivation is in docs/third-solve-algebra.pdf.Together 5.17 s to 4.61 s
6Whole arraysEach physics formula is called once on all its cells together, not cell by cell.
7Constants with NumPySimple sums in the build step are done in NumPy, which does not compile anything.
8Real parametersMasses, lengths and angles are stored as plain numbers, not complex ones. Square roots stay complex, because a reflectivity slightly above 1 otherwise gives "not a number" (found by a test that shifts every value by 0.1%).Together 4.61 s to 2.77 s
9No filler zerosThe formulas no longer build results that nobody reads.
10Leaner mirror formulaThe largest formula computes its shared angles and square roots once. Same results.
11Conversions on the hostTurning lists into JAX arrays compiled 36 tiny programs. Going through NumPy first avoids that.

Stage B: the calculation leaves JAX (changes 12 to 15)

No.ChangeWhat and whyEffect
12NumPy inside, JAX outsideThe physics formulas, the building of the equations and the gradient run in NumPy. JAX only sees a couple of calls. NumPy cannot compute gradients by itself, so the formulas run on a small number type that carries its own derivatives, and the rest of the gradient is written out by hand (and checked against JAX on 13 setups). The old JAX version is kept as a fallback for setups this path does not cover.2.77 s to 0.90 s
13No large memory pages (withdrawn)On a busy shared Linux machine one session showed runs of 0.74 s jumping to 2.8 s. Switching off NumPy's request for large memory pages looked like the cure.Cost 4% on a calm machine; benefit seen in one of two tests. Taken out.
14Derivatives only where neededA formula is differentiated only with respect to inputs that depend on a design value. Results identical bit for bit.Gradient step 131 ms to 110 ms (Linux)
15Frequencies reshaped in NumPyReshaping and copying the list of frequencies as a JAX array compiled two tiny programs.Build step 118 ms to 99 ms (Linux)

Stage C: a solver that lives in NumPy (changes 16 to 18)

No.ChangeWhat and whyEffect
16SciPy's sparse solver, all frequencies at onceThe equations of all 101 frequencies are stacked into one large table and factorised in one call. One factorisation serves the forward calculation and the gradient, where there were four per frequency. One polishing step (refinement) after each solve keeps the small numbers accurate. With the solver inside NumPy, JAX has even less to compile.Together 0.84 s to 0.71 s
17Dense tables stay outThe full tables, megabytes each, are no longer passed into the NumPy calls and kept for the gradient; only the few thousand entries that are needed travel.
18Lighter importsOnly the solver's own module is loaded, not the whole of SciPy's sparse package; the plotting library is loaded only when a plot is asked for.

Stage D: the last two hours (changes 19 to 21)

No.ChangeWhat and whyEffect
19Polish only where it mattersThe polishing step is kept for the solve that gives the noise, which depends on very small numbers. It is dropped for the solve that gives the signal. Two trial factorisations that picked the order of the equations are gone, because the solver's documentation says which order is right.Together: forward step 108 ms to 95 ms, gradient step 55 ms to 34 ms
20Build the equations onceThe gradient needs the same equations as the forward calculation, plus derivatives. They were built twice. Now the forward calculation builds them with derivatives and keeps them; the gradient picks them up with a ticket, and rebuilds them if the ticket is gone. Results identical bit for bit.
21Reuse memory on LinuxLinux handed every large block of memory back to the operating system when it was freed and fetched a fresh one next time. The package now asks it to keep freed memory.Gradient step 34 ms to 27 ms

5. The choices we made, and what we decided against

QuestionWhat we choseWhy, and what we turned down
Stay in JAX or leave it?NumPy for the work, JAX as the interfaceAfter changes 1 to 11 the first run was still mostly compiling. NumPy removes that. We kept the JAX function signature and the old JAX path as a fallback, so nothing a user relies on disappears.
Which sparse solver?First klujax, then SciPy's SuperLUklujax was fast but lived in the JAX program and factorised four times per frequency. A first attempt with SciPy passed the official check but was 0.7% off on a setup with a homodyne readout (limit 0.001%), so it was not used. The second attempt added a better order of the equations and the polishing step, and passed everything.
How strict is "same result"?Every output and all 193 gradient entries against the original, plus 19 other setupsThe official check looks at one gradient entry of 193, at about 2%. That is not enough to trust a rewrite of the gradient.
One gradient value disagreedInvestigate, then set the limit at 0.1% per entryA calculation without rounding showed that our value is right and the original's is 0.03% off, because of rounding in its dense solver. We changed the limit only after that was shown, and added a second limit for the gradient as a whole.
Keep the large-page switch?No (change 13 withdrawn)Its cost was certain (4%), its benefit was not. The way back is written down in case the scoring machine is a busy shared one.
Drop the polishing step entirely?No, only for the signalWithout any polishing all tests still pass, but the noise on the homodyne setup goes from 1e-12 to 1e-08 of the reference and the gradients from 6e-08 to 2e-06. That margin was worth more than 4 ms.
Change a process-wide memory setting?Yes (change 21)Unlike change 13 it is faster on a calm machine too, changes no number, and steps aside if the user has made their own setting. Its price: freed memory stays with the program.
Tricks around the timer?NoneLoading JAX before the benchmark's timer starts, or keeping compiled programs on disk between runs, would look faster. Both move work out of the timed part and were ruled out.
Replace a package's import to save 10 ms?Noklujax loads the package jaxtyping for one annotation. A stand-in would have saved about 3%, but it means interfering with another package's imports.
How to measure?A fresh process per sample, versions in shuffled rounds, same machine onlyThe scored number includes imports and compiling, so a warm loop measures the wrong thing. On the Mac the noise was 16%, so small changes were confirmed on one pinned Linux core, where each change showed up in its own phase.

Tried and not adopted

  • Sharing one factorisation inside klujax: about 3% of a first run, and it needs memory released by hand, where a mistake means a crash.
  • A polishing step for every klujax solve: more accurate than needed, 8% slower.
  • A hand-written gradient rule for the signal detector: about 2 ms, inside the noise, and it would lose one of JAX's modes.
  • More compiler settings, other solver settings: no gain; the ones in use are already the fastest we found.
  • Precomputing the index bookkeeping, slimming the build step further: 1 to 2 ms each.

7. How we know it is still right

  • The official check: both benchmarks print PASS. The distance from the public reference is 5.374e-06 in log sensitivity (limit 1e-5), the same as the original's own.
  • Against the original, number by number: every output and all 193 gradient entries (bench/validate.py), on the Intel Xeon, an AMD EPYC and the Mac. Sensitivity agrees to 6e-08 in log.
  • 19 other setups: other values, frequencies, layouts, readouts, grid sizes and modulation modes (tests/variations.py). 18 pass. One shows a deviation in two gradient values, and there the original is the one further from the exact answer.
  • NumPy path against JAX path: 13 cases plus finite differences for one design value of every kind (tests/test_host.py), and the 19 derivative rules derived by hand (docs/component-gradient-rules.pdf).
  • Stress test of v12: 24 random layouts from 1 Hz to 10 kHz, gradients asked for out of order and from six threads at once, memory over 300 evaluations (tests/stress.py). Passed on the Mac and on Linux.
  • From scratch: a fresh clone from GitHub with a fresh environment from requirements.txt runs both benchmarks and the checks to PASS.

8. What we learned

  • Find where the time goes before changing anything. The first surprise was that compiling, not arithmetic, was most of a run. The last was that half of what is left is one import.
  • One change at a time. Each could be measured, checked and, like change 13, taken out again.
  • A fast wrong answer is worth nothing. The first SciPy attempt passed the official check and was still wrong on another setup. Only the wider tests caught it.
  • The reference can be the inaccurate one. When ours and the original disagreed on one gradient value, a calculation without rounding settled it.
  • Noise decides what you may claim. Several changes were real in their own phase and invisible in the total on a laptop. We claimed them only after a pinned Linux core showed them.
  • A merge can undo a decision. The inaccurate SciPy experiment once reached main by mistake; the tests showed it within minutes.

9. Known limits and open points

  • The NumPy path computes gradients in reverse mode only, and only with respect to the design values. Setups with custom linking functions take the slower JAX path (about 2.5 s on the judges' processor type).
  • A negative reflectivity gives "not a number" in ours and a number in the original. The optimisation examples bound reflectivities to 0 to 1.
  • On a busy shared machine an earlier version showed first runs between 0.74 and 2.8 s. If the scoring machine is such a machine, NUMPY_MADVISE_HUGEPAGE=0 is the setting to try.
  • The single-run official report of v12 on the Intel Xeon is not in the repository (the ten-run session and the check against the original are). python bench/run.py official --versions v12-kept-assembly on that machine produces it.
  • The repository is private: the judges need access, or it has to be made public.
